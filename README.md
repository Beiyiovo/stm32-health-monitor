# STM32 健康监测设备（毕业设计）

> 基于 **STM32F103C8T6** 的多参数健康监测设备原型：采集体温 / 心率血氧 / 运动姿态，
> 在 OLED 上本地显示，并通过 ESP32-C3 无线上报，异常时蜂鸣器与 LED 报警。
>
> 状态：**开发中**。外设驱动逐个验证，完整主程序 `09_main` 尚未整机联调。

最近更新：2026-10-12

## ★ 先看这个：`flash_any.bat` —— 一键烧录工具

这是本仓库最实用的东西，**一个双击完成"编译 → 转 bin → 找串口 → 握手 → 烧录"全流程**，
不用打开 Keil、不用记命令行、不用手动找 `.hex`。

```
双击 flash_any.bat
  → 列出全部 24 个工程（带中文说明）
  → 输入编号
  → 自动编译（调 UV4.exe 命令行）
  → 自动 fromelf 把 .axf 转成 .bin
  → 自动找到 CH340 串口
  → 自动扫描波特率并烧录
  → 提示你拨回 BOOT0 + 复位
```

### 它解决的问题

STM32 的串口 ISP 烧录（USB-TTL + BOOT0）在**面包板 + 长杜邦线**上极不稳定：
波特率稍高就握手失败，串口被别的程序占着就整个烧不进去，失败时报错信息还很难懂。
这个工具把这些问题都做进去了：

| 机制 | 为什么需要 |
|---|---|
| **波特率自动扫描** | 按 `38400 → 19200 → 9600` 依次试，找到**能握手的那个**再用它烧。而不是死磕一个波特率反复重试——那正是早期版本失败的根因 |
| **批量轰炸握手（`try_sync_fast`）** | 一次连发 8 个 `0x7F` 再一次性读，而不是"发一个等一个"。避开了每次读超时的等待，**握手速度翻倍**。原理是 STM32 bootloader 收到任意一个完整的 `0x7F` 就会回 `0x79`，所以根本不用等 |
| **串口占用检测** | 开烧之前先试着独占串口，失败重试 3 次，然后明确告诉你"**`serial.bat` 还开着吗？**"。这是烧录失败最常见的原因，但原始报错完全看不出来 |
| **失败自动降速重试** | 用握手成功的波特率烧，失败则依次降档（38400→19200→9600→4800） |
| **工程编号 + 中文说明表** | 24 个分步工程，不用记哪个目录是干嘛的 |
| **具体到线的排查提示** | 连不上时直接提示 `TXD→A10 / RXD→A9 / GND→G`、试试 TXD/RXD 对调、杜邦线换短的 |

> 速度：作者实测烧 27 KB 固件，**38400 约 7 秒 / 19200 约 15 秒 / 9600 约 30 秒**。
> （未在本仓库做独立基准测试，数字来自开发时的实测记录。）

### 它是怎么演进出来的

源码注释里保留了完整的演进轨迹，这段比工具本身更有意思：

- **v3 / v4**：直接调 `stm32loader` 反复重试 → **一直不成功**
- **v5**：回到最早成功过的思路 —— **先用 Python 直接发 `0x7F` 扫波特率**，找到能握手的，再用那个波特率调 `stm32loader` 烧
- **v6.1**：握手改成**保持串口打开 + 批量轰炸**，避开逐个超时等待
- **v6.2**：烧录阶段失败自动降速重试；新增串口占用检测

> 关键教训：**先确认物理链路能握手，再谈烧录**。早期版本跳过握手直接烧，失败时根本分不清是线的问题、波特率的问题、还是串口被占用的问题。

| 模块 | 型号 | 接口 | 作用 |
|---|---|---|---|
| 主控 | STM32F103C8T6（蓝板） | — | 采集、显示、报警、串口通信 |

| 报警 | 蜂鸣器 + LED + 按键 | GPIO | 阈值报警与交互 |

## 另一个亮点：一次完整的 I2C 总线排查

完整记录在 [`说明.md`](说明.md)。

**症状**：扫描不到任何 I2C 设备，但电压正常、引脚能拉高拉低、连线全通。

**定位到的三个根因**：

1. **硬件 I2C 外设不可靠**（STM32F103 的经典问题）→ 改为 **GPIO 软件模拟 I2C**
2. **总线速率太快** → `I2C_DELAY_US = 20`（≈25 kHz）才稳定，5 μs（≈100 kHz）扫不到
   - 物理解释：面包板 + 杜邦线的分布电容远大于 PCB，I2C 是开漏总线，上升沿靠上拉电阻给电容充电，
     速率快时电平还没建立主机就采样 → 从机收到乱码 → 不应答
3. **`I2C_Send7bitAddress` 实际要传 8 位地址** → 之前扫到 0x78/0x79（8 位）而非期望的 0x3C（7 位）

**诊断方法**：用 `16_i2c_scope`（自己写的软件示波器）把每一位电平打印出来，
观察第 9 位 ACK 时 SDA 是否被从机拉低 → 实测 0x3C 的 ACK=1，证明模块与总线都是好的，问题在主控侧。

> 同一限制也影响烧录：串口 ISP 用 9600 最稳，115200 从未成功过。

## 快速开始

1. `pip install -r requirements.txt`
2. 用 Keil MDK-ARM 5 打开想验证的工程（如 `01_uart/step1_uart.uvprojx`）
3. 双击 **`flash_any.bat`**，输入工程编号，按屏幕提示操作：

   ```
   ① BOOT0 跳线帽 → 1
   ② 按一下复位键（RST）
   ③ 脚本开始扫描波特率 → ★ 反复按复位键，直到屏幕显示「握手成功」
   ④ 自动烧录
   ⑤ 烧完：BOOT0 → 0
   ⑥ 再按一下复位键      ← 这两步漏了程序不会跑
   ```

   > 或者买一个 ST-Link V2（约 20 元）：Keil 里按 F8 三秒烧完，不用拨跳线、不用按复位。

4. 看串口输出：双击 `serial.bat`
